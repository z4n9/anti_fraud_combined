# Архитектура Family Bank и Family Guard

Актуальное реализованное состояние на 4 ноября 2026. Один FastAPI-сервис обслуживает клиентский Family Bank на `/` и кабинет Family Guard на `/analyst/`. Соседние исходные проекты не используются во время запуска. Совместимые технические имена — [branding.md](branding.md).

## Потоки данных

```mermaid
flowchart TB
    BANK["Family Bank: клиент и родственники"] --> AUTH["Cookie-сессия и серверные права"]
    GUARD["Family Guard: аналитик"] --> AUTH
    AUTH --> TRANSFER["POST /api/transfers"]
    TRANSFER --> SCORE["fraud_detector: правила, граф и LightGBM"]
    SCORE --> POLICY["transfer_approval_service: добровольная защита, кворум, AntiScam"]
    POLICY --> MONEY["bank_service: атомарные проводки и аудит"]
    MONEY --> DB[("Банковская SQLite")]
    AUTH --> ANALYSIS["/api/analyst: импорт, план, анализ, расследование"]
    ANALYSIS --> STORAGE[("Приватное аналитическое хранилище")]
    AUTH --> MONITOR["GET /api/analyst/recipient-monitoring"]
    DB --> MONITOR
    STORAGE --> MONITOR
    MONITOR --> SIGNAL["Независимый сигнал небольших поступлений"]
```

## Перевод и семейная политика

`POST /api/transfers/risk-check` возвращает предварительный риск, `family_protection_active` и `requires_risk_acknowledgement`, не исполняя перевод. `POST /api/transfers` повторно вычисляет решение на сервере; preview не предоставляет разрешение на списание.

Команда принимает обязательный `Idempotency-Key`, изолированный по пользователю. Под SQLite `BEGIN IMMEDIATE` обновляются ранее загруженные сущности, проверяются карта, сумма, баланс, настройки защиты и участники. При выключённой защите high/critical требует строгого `risk_warning_acknowledged=true`; без подтверждения HTTP 428 и отсутствие списания. После подтверждения перевод допускается, если отдельный AntiScam не требует `bank_review`.

При включённой защите высокий риск создаёт `TransferRequest` со статусом `pending_approval` и фиксированным составом до трёх `TransferParticipant`. До первого ответа денег не списывают. Первый approve разрешает исполнение с учётом AntiScam, первый reject окончательно отклоняет; остальные ответы получают 409. Сотрудник не обходит отсутствие семейного одобрения. Включённая защита без действующего согласия даёт `blocked_no_trusted`. Сумма и получатель неизменны; для других реквизитов создаётся новая заявка. Истечение — 24 часа, деньги не резервируются.

| API | Полномочия |
| --- | --- |
| `GET /api/transfers/requests` | Собственные запросы отправителя |
| `GET /api/transfers/pending-requests` | Запросы назначенного родственника |
| `POST /api/transfers/requests/{request_id}/approve` или `/reject` | Проверенный участник конкретного запроса |
| `POST /api/transfers/requests/{request_id}/cancel` | Отправитель в допустимом состоянии |
| `GET /api/analyst/bank-events` и `/{request_id}` | Сотрудник с ролью analyst, без загрузки файла |
| `POST /api/analyst/bank-events/{request_id}/approve` или `/reject` | Сотрудник, только bank_review, обязательное основание |

`bank_service.post_transfer` не делает отдельный commit: условное списание при достаточном балансе, зачисление, обе проводки, итог запроса и аудит фиксируются одной транзакцией. Деньги хранятся целыми тиынами. `risk_json` и `policy_json` сохраняют момент оценки и подтверждение предупреждения. `anti_scam_json` хранит nullable boolean ответы отдельно от численного риска. `BankReviewDecision` фиксирует автора и основание с уникальностью на запрос.

## Семейные связи

`TrustedInvitation` хранит адресное назначение, проверку родства и согласие. До трёх pending/accepted приглашений могут сосуществовать. `TrustedPerson` содержит глобальные настройки и совместимую сводку первой принятой связи. Приглашения обслуживаются `/api/trusted-invitations`, Mock eGov — `/api/mock-egov/verify-relationship`.

`ProtectionChangeRequest` создаётся через `POST /api/protection-change-requests`: отключение либо адресное удаление с `invitation_id`. Ожидание — 24 часа с отменой. До срока семейные полномочия действуют; после срока отключение сохраняет принятое приглашение, удаление отзывает адресную связь. Решает один действующий участник из зафиксированных кандидатов. При AntiScam банк повторно проверяет именно одобрившего родственника. Сроки применяются при обращениях к API, фонового обработчика нет. Контракты — ADR-012/013/016.

## Аналитика и мониторинг

Роль `analyst` проверяется сервером через общую сессию. Собственные файловые анализы имеют владельца, чужие ID не предоставляют доступ. API `/api/analyst/analyses` принимает структурированные файлы; SQLite открывается для чтения, SQL разбирается без исполнения. План, запуск, расследование, объяснения и экспорт не меняют банковские деньги. Результаты находятся в приватном runtime, модельные артефакты — в отдельном приватном registry. Профиль транзакций работает на правилах без ML; клиентский CatBoost-профиль явно недоступен без доверенной модели.

`GET /api/analyst/recipient-monitoring` читает до 50 000 завершённых банковских дебетов с проверенными кредитовыми парами либо до 100 000 результатов собственного завершённого анализа. Независимый движок ищет сильнейшее историческое 60-минутное окно: ≥10 небольших переводов ≤10 000 KZT, ≥8 новых отправителей, доля новых ≥80%. Новизна определяется доступной предшествующей историей. Runner сохраняет исходную сумму и валюту без изменения оценок. Страница показывает причины, отправителей и до 200 операций, раскрывает усечение и ограничения. Это чтение, без изменения банковского скоринга, проводок или таблиц. Контракт — [recipient-monitoring.md](recipient-monitoring.md), ADR-017.

## Деплой и хранение

Dockerfile собирает React на Node 24 и копирует dist в Python 3.13 runtime. Один Uvicorn worker обслуживает оба интерфейса; только разрешённые глубокие ссылки аналитика получают SPA fallback. `/api/readiness` проверяет хранилище и сборку UI. Закрытые БД, файлы и исходники не раздаются браузеру. Same-origin guard защищает изменяющие запросы, API возвращает `Cache-Control: no-store`.

Compose по умолчанию слушает `127.0.0.1`; внешний HTTPS требует reverse proxy. Непривилегированный процесс, read-only root filesystem и постоянный том `/data`. Multipart spool находится в `/data/upload-tmp`, `/tmp` остаётся tmpfs 256 МиБ. На диске могут одновременно существовать spool и staged copy; планируйте около 2×размера файла плюс результаты и БД. Миграции создают backup и сохраняют строки/индексы; проверяется целостность внешних ключей.

SQLite и задания в одном процессе ограничивают масштабирование. Реальные платёжные сети, eGov, внешние уведомления, валидированная ML-модель и промышленный пилот не подключены. Запуск, backup и восстановление — [DEPLOYMENT.md](../DEPLOYMENT.md).

## Первый семейный ответ и совместимость — ADR-019

Новые запросы сохраняют `policy_version=family-v4-first-response` и `required_family_approvals=1`. До трёх `TransferParticipant` остаются фиксированными кандидатами. `policy_json.family_decision` фиксирует первого ответившего, приглашение, ответ и время. Ответ, статус и проводки атомарны под SQLite write lock; неуспешная проводка откатывает и ответ. Дубликат сохранённого ответа идемпотентен, поздний ответ другого кандидата запрещён.

При чтении/команде старый pending без голосов обновляет политику без денег. Старый pending с голосами отменяется с `resolution_note`, без автоматического исполнения. Исторический bank_review сохраняет старую политику согласования. Дополнительных таблиц или столбцов не требуется. Изменяющая настройки защита сохраняет ожидание 24 часа.

`core/demo_credentials.py` задаёт восемь демо-паролей; seed ротирует только прежние стандартные/пустые хэши и сохраняет пользовательские. Хранение остаётся scrypt, логины TEST и роли не меняются.

## Встроенный банковский ML — ADR-020

`app/ml/` содержит доверенные assets, модель, исходные features/правила/OOD и read-only MemoryHistory. `services/ml_history.py` строит ограниченную, дедуплицированную проекцию банковских запросов и старых парных переводов на момент решения. `FraudDetector` объединяет решения без снижения исходного риска; ML не управляет проводками напрямую. Снимок аудита хранится в существующем policy_json, изменений таблиц не требуется.

Банковские preview/команды возвращают engine_mode=hybrid_ml_rules при доступной модели, иначе rule_based_fallback и ml.status. Признаки и raw score остаются приватными, аналитик получает whitelist ml_assessment. `/api/health` диагностирует онлайн-модель, `/api/readiness` учитывает required/неверный режим. Конфигурация auto|required|off и демонстрационный FX описаны в ADR020/README. Docker содержит LightGBM, PyYAML, libgomp1 и assets, отдельный сетевой сервис не нужен. Аналитические файловые модели кабинета работают отдельно.

## Нативные денежные признаки KZT — ADR-021

Runtime app/ml/history получает целые тиыны и передаёт модели amount_cents/100 в тенге. Модель имеет адаптированные денежные split-thresholds/feature_infos, конфиг и OOD в KZT. Нет динамического FX, EUR-округления или минимума5₸. Исходный масштаб500 зафиксирован только в provenance офлайн-преобразования; ratio/time/counts и листья не изменены. Новые audit/status содержат currency/model_currency=KZT, unit_version=kzt-native-v1, amount_kzt, monetary_thresholds_kzt. Staff whitelist выдаёт эти поля; старый demo_kzt_per_eur допускается только для исторического снимка прежней версии.

Перенос единиц не является локальной перекалибровкой. Существующие правило80%, семейное согласование, строгая история, сохранённый audit и финансовые транзакции не меняются. Проверки native/source forecast parity и происхождения описаны в testing.md/ADR-021.

## Контекст баланса банковской ML-проверки — ADR-022

`fraud_detector` передаёт серверный баланс активной карты в `ml.service.evaluate_synsepa(sender_balance_cents=...)`. Гибридный контур сохраняет баланс до перевода, долю суммы и расчётный остаток в приватном `balance_context`. Балансный снимок не входит в клиентский, родственный или аналитический публичный контракт. Веса и 21 признак LightGBM сохранены.

По ADR-023 сравнение с 80% выполняется после исходного `REVIEW` от модели либо в резервном режиме правил. Результат хранится в отдельном приватном `balance_rule`, поэтому он не меняет решение исходных защитных правил. Банк объединяет сигналы модели, доли, правил и графа по максимальному риску. Проверка наличия средств всегда выполняется независимо.
