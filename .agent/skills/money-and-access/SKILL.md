# Навык: Денежные операции и доступ

Этот навык обязателен для любого агента или субагента, модифицирующего модели данных, логику списаний, зачислений, проверок баланса и прав доступа пользователей и родственников.

---

## 1. Точность и представление денег

- **Строго целочисленные тиыны в базе**:
  - 1 тенге (KZT) = 100 тиынов.
  - В SQLite / SQLAlchemy поле баланса и суммы транзакции имеет тип `Integer`.
  - Запрещено использовать `Float`, `Real` или неточные типы с плавающей точкой в БД для хранения финансовых сумм.
- **Преобразование на границе API**:
  - Входные данные API принимаются в тенге (число с плавающей точкой или строка). Валидатор проверяет: сумма строго > 0, не более 2 знаков после запятой, нет NaN, Infinity или переполнения.
  - Конвертация: `cents = int(round(amount * 100))`.
  - Ответ API возвращает тенге: `balance / 100` или `amount / 100`.

---

## 2. Атомарность и предотвращение перерасхода (Overdraft)

- **Отказ от "read-then-update"**:
  - Нельзя читать баланс `SELECT balance`, проверять в Python `if balance >= cents:` и затем делать `UPDATE cards SET balance = ...`. В многопоточной среде это приводит к состоянию гонки (race condition) и отрицательному балансу.
- **Условный UPDATE в базе**:
  ```python
  balance = db.scalar(
      update(Card)
      .where(Card.id == card_id, Card.balance >= cents)
      .values(balance=Card.balance - cents)
      .returning(Card.balance)
  )
  if balance is None:
      db.rollback()
      raise HTTPException(400, "Недостаточно средств")
  ```
- **Единая транзакция**:
  - Списание с карты отправителя, зачисление на карту получателя и создание двух записей в истории транзакций (расход и доход) должны выполняться строго в пределах одной транзакции базы данных (`BEGIN IMMEDIATE` / `db.commit()`).
  - При любой ошибке (включая сбой записи истории получателя) выполняется немедленный `db.rollback()`, и балансы возвращаются в исходное состояние.

## 3. Идемпотентность

- **Заголовок `Idempotency-Key`**:
  - Изолирован по пользователю: ключ формируется как `{current_user_id}:{idempotency_key}`.
  - При повторном запросе с тем же ключом и идентичными параметрами (получатель, сумма, сообщение): возвращается сохранённый результат предыдущего успешного перевода БЕЗ повторного списания.
  - При повторном запросе с тем же ключом, но изменившимися параметрами: сервер обязан вернуть `409 Conflict` ("Этот ключ уже использован для другого перевода").

---

## 4. Разграничение доступа и семейное подтверждение

1. **Изоляция финансовых данных**:
   - Пользователь имеет доступ ТОЛЬКО к своим картам, транзакциям и балансам (`Card.user_id == current_user.id`).
   - Получатель или родственник не может просматривать баланс или полную выписку другого пользователя.
2. **Семейная защита и статус перевода**:
   - При срабатывании правил высокого риска перевод переходит в статус `pending_approval`.
   - **До момента одобрения деньги со счёта отправителя НЕ списываются**.
   - **Отправитель не имеет технической возможности подтвердить свой собственный рискованный перевод**. Попытка вызова подтверждения от имени отправителя возвращает `403 Forbidden`.
   - Только верифицированный родственник (`relationship_verified == True` и `invitation_status == 'accepted'`) имеет право подтвердить (`approve`) или отклонить (`reject`) операцию.
   - Право подтверждения относится **исключительно к конкретной транзакции** с фиксированными реквизитами (ID перевода, сумма, получатель). Оно **НЕ** предоставляет родственнику общего доступа к кошельку или права произвольного списания.
   - Если сумма или получатель изменяются, прежнее согласование аннулируется.
   - Если у пользователя нет доверенного лица или приглашение не принято, перевод высокого риска **не может быть исполнен автоматически**.
