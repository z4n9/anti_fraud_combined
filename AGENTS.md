## 1. Цель проекта и контекст
Создание единой модульной банковской системы с антифродом и семейной защитой в репозитории `anti_fraud_arrt`.
Система объединяет клиентский банк **Family Bank** (`anti_fraud_1`) и аналитический сервис **Family Guard** (`FraudBanc`).

## 2. Текущий продукт и границы
- Family Bank — клиентский банк; Family Guard — добровольная семейная защита и кабинет аналитика.
- На 15 октября 2026 реализованы переводы с точностью до тиына, до трёх родственников и их фиксированные голоса, банковское решение при конфликте, AntiScam, задержка ослабления защиты 24 часа, загрузка/расследование/экспорт и мониторинг получателей небольших переводов.
- Политика: ADR-016 (вне защиты предупреждение и явное подтверждение отправителем; в активной защите семейное согласование). Мониторинг получателей — ADR-017, только аналитика, без изменения банковских решений.
- Последний полный прогон после ребрендинга: backend 379 passed / 7 skipped; frontend 70 passed, lint/build. Браузерная и Docker-проверки выполнены; подробности — docs/testing.md.
- Переносимый Docker-деплой подготовлен. Реальный банковский пилот, внешние уведомления и обучение ML остаются отдельным backlog; автоматически не начинать.
- Сохранять техническую совместимость: AMAN_* env, aman_bank.db, aman_session, compose service aman / volume aman-data, frontend/aman, app.risk_ledger, существующие localStorage ключи и тестовые пароли. Пользовательские названия — только Family Bank / Family Guard. Источники anti_fraud_1 и FraudBanc не переименовывать. Подробнее docs/branding.md.

## 3. Команды исходных проектов (результаты см. docs/testing.md)
Основные команды запуска и проверки относятся к целевому проекту; команды соседних исходников приведены только для сравнения.

### Запуск и тесты нового банковского ядра
Из `anti_fraud_arrt`:
```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
powershell -ExecutionPolicy Bypass -File .\test.ps1
```
`test.ps1` выбирает локальное `.venv` либо подготовленное `../test_env`; тесты используют временные базы. В sandbox Windows требуется разрешённый доступ к каталогам pytest с mode 0700. Полные результаты и ограничения — в docs/testing.md.

### Сравнение с исходными проектами
```powershell
# Запуск тестов банковского ядра (32 теста, 100% pass):
..\test_env\Scripts\python.exe -m pytest ..\anti_fraud_1\backend\tests -v

# Запуск тестов правил антифрода:
..\test_env\Scripts\python.exe -m pytest ..\FraudBanc\backend\tests\unit\test_transaction_rules.py -v
```

### Запуск и тесты фронтенда (Family Guard)
*Важно: на Windows использовать `npm.cmd`.*
```powershell
npm.cmd ci --prefix frontend/analyst
npm.cmd --prefix frontend/analyst test -- --run
npm.cmd --prefix frontend/analyst run lint
npm.cmd --prefix frontend/analyst run build
```

## 4. Критические правила: база данных, API и деньги

1. **Точность денег:** В базе данных деньги хранятся **строго целыми тиынами** (`Integer`, 1 KZT = 100 тиынов). Никаких `Float`/`Real` в SQLite!
2. **Атомарность операций:** Списание у отправителя, зачисление получателю и запись в журнал транзакций выполняются **в одной транзакции** базы данных.
3. **Защита от овердрафта:** Списание выполняется атомарным условным запросом:
   `UPDATE cards SET balance = balance - :cents WHERE id = :id AND balance >= :cents`.
4. **Идемпотентность:** Заголовок `Idempotency-Key` обязателен для переводов, изолируется префиксом `{user_id}:{key}`.
5. **Семейное подтверждение при высоком риске:**
   - Семейная защита добровольна. При выключенной защите high/critical требует предупреждения и явного `risk_warning_acknowledged=true`; без него сервер возвращает 428 без списания. После подтверждения перевод исполняется, кроме отдельной проверки AntiScam.
   - При включённой защите высокий риск переводит транзакцию в статус `pending_approval`, если есть действующие согласившиеся родственники.
   - До одобрения деньги со счёта отправителя **не списываются**.
   - Отправитель **не может** сам проголосовать за перевод, направленный на семейное согласование (`403 Forbidden`). Подтверждение предупреждения вне защиты не является семейным голосом.
   - Назначаются до трёх верифицированных родственников с личным согласием; участники фиксируются при создании перевода.
   - При нескольких участниках требуются все ответы. Единогласное одобрение исполняет перевод, единогласный отказ отклоняет, конфликт передаёт окончательное решение сотруднику банка (bank_review).
   - Сотрудник analyst решает только банковскую проверку с обязательным основанием и атомарным аудитом. Незавершённые голоса, истёкший срок и утрата семейных полномочий не дают права исполнить перевод.
   - Тревожный ответ AntiScam требует банковской проверки; высокий риск сначала проходит семейное голосование. Неизвестный ответ не считается «Нет».
   - Изменение суммы или получателя требует нового согласования.
   - При включённой защите и отсутствии действующего доверенного лица высокий риск остаётся `blocked_no_trusted`. Отключение/удаление сохраняет ожидание 24 часа; старые запросы не получают автоматического исполнения после изменения настроек. Актуальная политика — ADR-016.

## 5. Порядок использования субагентов
Для работы определены 4 специализации субагентов (роли для доступного механизма делегирования; отдельных конфигураций агентов в репозитории пока нет):
- `backend-data`: FastAPI, роутеры, SQLAlchemy, миграции, целостность транзакций.
- `frontend`: Family Bank mobile UI, Family Guard analyst dashboard, обработка ошибок, состояния загрузки.
- `antifraud`: правила, признаки, BoundedTransactionGraph, объяснения, адаптеры моделей.
- `quality-security`: независимый аудит прав доступа, финансовых операций, защита от гонок (race conditions) и регрессионное тестирование.

**Правила совместной работы:**
- Одновременно активно не более 3 субагентов (плюс агент-координатор).
- За каждым субагентом закрепляются изолированные файлы или модули.
- Изменение общих контрактов API и моделей БД согласовывается через координатора.
- Проверку качества и безопасности всегда проводит агент `quality-security`, не писавший проверяемый код.
