## 3. Команды исходных проектов (результаты см. docs/testing.md)
Окружение и банковские тесты повторно проверены. Аналитические/frontend-команды ниже относятся к исходному FraudBanc и на этапе 2 не запускались.

### Запуск и тесты нового банковского ядра
Из `anti_fraud_arrt`:
```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
powershell -ExecutionPolicy Bypass -File .\test.ps1
```
`test.ps1` выбирает локальное `.venv` либо подготовленное `../test_env`; тесты используют временные базы. В sandbox Windows требуется разрешённый доступ к каталогам pytest с mode 0700. Полные результаты и ограничения — в docs/testing.md.

### Сравнение с исходными проектами
```powershell
# Запуск тестов банковского ядра (32 теста, 100% pass):
..\test_env\Scripts\python.exe -m pytest ..\anti_fraud_1\backend\tests -v

# Запуск тестов правил антифрода:
..\test_env\Scripts\python.exe -m pytest ..\FraudBanc\backend\tests\unit\test_transaction_rules.py -v
```

### Запуск и тесты фронтенда (Risk Ledger)
*Важно: на Windows использовать `npm.cmd`.*
```powershell
npm.cmd ci --prefix ..\FraudBanc\frontend
npm.cmd --prefix ..\FraudBanc\frontend test -- --run
npm.cmd --prefix ..\FraudBanc\frontend run lint
npm.cmd --prefix ..\FraudBanc\frontend run build
```

## 4. Критические правила: база данных, API и деньги

1. **Точность денег:** В базе данных деньги хранятся **строго целыми тиынами** (`Integer`, 1 KZT = 100 тиынов). Никаких `Float`/`Real` в SQLite!
2. **Атомарность операций:** Списание у отправителя, зачисление получателю и запись в журнал транзакций выполняются **в одной транзакции** базы данных.
3. **Защита от овердрафта:** Списание выполняется атомарным условным запросом:
   `UPDATE cards SET balance = balance - :cents WHERE id = :id AND balance >= :cents`.
4. **Идемпотентность:** Заголовок `Idempotency-Key` обязателен для переводов, изолируется префиксом `{user_id}:{key}`.
5. **Семейное подтверждение при высоком риске:**
   - Высокий риск переводит транзакцию в статус `pending_approval`.
   - До одобрения деньги со счёта отправителя **не списываются**.
   - Отправитель **не может** сам подтвердить свой перевод (`403 Forbidden`).
   - Только верифицированный родственник подтверждает или отклоняет конкретный перевод из своего аккаунта.
   - Изменение суммы или получателя требует нового согласования.
   - При отсутствии доверенного лица перевод высокого риска не исполняется автоматически.

## 5. Порядок использования субагентов
Для работы определены 4 специализации субагентов (роли для доступного механизма делегирования; отдельных конфигураций агентов в репозитории пока нет):
- `backend-data`: FastAPI, роутеры, SQLAlchemy, миграции, целостность транзакций.
- `frontend`: AMAN Bank mobile UI, Risk Ledger analyst dashboard, обработка ошибок, состояния загрузки.
- `antifraud`: правила, признаки, BoundedTransactionGraph, объяснения, адаптеры моделей.
- `quality-security`: независимый аудит прав доступа, финансовых операций, защита от гонок (race conditions) и регрессионное тестирование.

**Правила совместной работы:**
- Одновременно активно не более 3 субагентов (плюс агент-координатор).
- За каждым субагентом закрепляются изолированные файлы или модули.
- Изменение общих контрактов API и моделей БД согласовывается через координатора.
- Проверку качества и безопасности всегда проводит агент `quality-security`, не писавший проверяемый код.
